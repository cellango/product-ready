What Product Ready Does

Core principle
Product Ready ensures all product work is clear, testable, measurable, OKR-aligned, and traceable before it reaches engineering. If it is not testable and measurable, it is not Product Ready.

🎯 For Product Owners

  • Guides from vague idea to complete BDD Spec
  • Enforces 18 non-negotiable guardrails
  • Scores spec quality before AI generation
  • Links every feature to an OKR
  • Produces structured prioritization with justification

🤖 For AI Code Generation

  • BDD Spec → self-contained AI prompts
  • Concrete test data in every scenario
  • Observable Then clauses (UI/API/DB/log)
  • Pass/fail conditions per scenario
  • Automation readiness classification

🔗 For Engineering Teams

  • Requirements Traceability Matrix (RTM-lite)
  • Bidirectional REQ ↔ BS ↔ TS linkage
  • Zero orphan scenarios or test cases
  • Acceptance criteria before a line of code
  • Coverage verified, not assumed

The 13-Step Adaptive Workflow

Product Ready uses one workflow with adaptive depth — Lightweight, Standard, or Full — chosen automatically based on complexity, risk, and compliance signals.

1
Step 1
Product Strategy / Goal
Define business objective, customer problem, and SMART success metric. Establish OKR linkage: which Objective (OBJ-*) and Key Result (KR-*) does this work serve?
1b
Prioritization Gate 1 — Strategic
Strategic Prioritization
Score the initiative on strategic alignment, customer impact, business value, and confidence. Declare: why now, what NOT doing, consequence of a one-quarter delay. Low score → deprioritize. Do not proceed to Discovery.
2
Step 2
Discovery / Validation
Clarify problem, user, current workflow, and desired outcome. Validate assumptions with the cheapest possible test. Define success and failure criteria.
3
Step 3
Challenge (Drill-Me)
Critically evaluate assumptions, risks (value/usability/feasibility/viability), missing decisions, and simpler alternatives. Challenge the OKR alignment: is this the right lever for the Key Result? Is the contribution hypothesis falsifiable?
3b
Prioritization Gate 2 — Solution
Solution Prioritization
MoSCoW triage on candidate capabilities. Score alternative approaches. PRD scope must contain only Must + approved Should items. Won't items become explicit non-goals in the PRD.
4
Step 4
PRD — Product Requirements Document
Produce structured product definition: requirements (REQ-*), business rules (BR-*), goals and non-goals, SMART metrics, dependencies. Include OKR section: contribution hypothesis and validation plan (leading indicator, lagging KR metric, attribution approach).
REQ-*BR-*OKR section
5
Step 5 — THE SPEC
BDD Spec (THE SPEC)
Define BDD scenarios (BS-*) in Given / When / Then format. Cover happy paths, failure scenarios, edge cases, UI states, and security scenarios. Every scenario: concrete test data, observable Then clause naming a system layer (UI/API/DB/log/event), pass and fail conditions. Apply Spec Integrity gate (Guardrail #8) before proceeding.
BS-*
5b
Step 5b — Optional
Generate from Spec
Activates on "generate tests" or "generate code from spec". Runs Spec Quality Score. If Complete: formats each BS-* as a self-contained AI generation prompt — one ready-to-paste block per scenario with test data, pass/fail conditions, and automation level.
6
Step 6
Test Spec
Convert BDD scenarios into test cases (TS-*) — steps, assertions, automation level (Automatable / Partially automatable / Manual only). After completion, apply Acceptance Coverage (Guardrail #9) and generate RTM-lite (Guardrail #10).
TS-*RTM-lite
7
Prioritization Gate 3 — Delivery
Delivery Prioritization
RICE scoring (Reach × Impact × Confidence / Effort). Cost of Delay for urgency signals (WSJF). Every item: mandatory justification (why this over that) and trade-off declaration for items ranked below. Ranked backlog output.
Ranked backlogTrade-off log
8
Step 8
Issues
Break into independent, testable stories. Each story linked to REQ-* / BS-* / TS-*. Export to Jira or Linear.
9
Step 9
Build
Implementation follows BDD Spec. All open questions resolved before coding begins. Any deviation from spec triggers a spec update — not a code workaround.
10
Step 10
Acceptance
Acceptable when: all Must scenarios pass, tests pass, no critical defects, UI/UX acceptable, RTM-lite complete (every REQ-* has BS-* and TS-*), no orphans, automation readiness ≥80%.
11
Step 11
Release
Readiness checklist, stakeholder alignment, rollback plan exists.
12
Step 12
Measure
Report at two levels: feature metric (leading indicator) AND KR movement (lagging OKR metric). If KR did not move despite feature metric being met → causal chain was wrong → revisit contribution hypothesis.
13
Step 13
Learn / Iterate
Evaluate what worked, what failed, hypothesis verdict. Feed back into Discovery and re-prioritization.

Multi-Level Prioritization Framework

The critical insight
Prioritization placed only after the PRD is too late. By then teams have invested effort, anchored on a solution, and created sunk-cost pressure. Prioritization must happen before each major investment — at three distinct levels.
1
Strategic
Before Discovery
"Should we work on this problem at all?"
  • Strategic alignment score
  • Customer impact score
  • Business value score
  • Confidence score
  • Opportunity cost declaration
  • Consequence of delay
2
Solution
Before PRD
"Which approach and scope should we pursue?"
  • MoSCoW triage (Must / Should / Could / Won't)
  • Option scoring (Impact / Effort / Risk)
  • Scope boundary definition
  • Won't items → PRD non-goals
3
Delivery
Before Issues
"What do we build first within confirmed scope?"
  • RICE: Reach × Impact × Confidence / Effort
  • Cost of Delay (WSJF) for urgency signals
  • ICE for simple triage
  • Justification + Trade-off per item

Prioritization Frameworks at a Glance

FrameworkFormulaBest used when
RICE Reach × Impact × Confidence / Effort Maximizing user value across a portfolio of features
WSJF Cost of Delay / Job Size Urgency-driven decisions, deadline pressure, or revenue impact
ICE Impact × Confidence × Ease Quick backlog triage when full RICE data is unavailable
MoSCoW Must / Should / Could / Won't Scope decisions for a release or sprint

18 Non-Negotiable Guardrails

Every output is checked against all applicable guardrails before proceeding to the next step. Guardrails are never weakened by policy.

Spec Quality — Guardrails 1–8

#GuardrailWhat it blocks
1No Missing Decisions — TBDs flagged as Missing Product Decisions before reaching engineeringAmbiguous requirements entering the build
2Testability Rule — untestable requirements blocked; must have acceptance criteria and test casesRequirements with no observable success criterion
3No Duplicates or Conflicts — conflicting rules normalized to BR-* format and resolvedContradictory requirements reaching engineering
4Metric Integrity — every metric must have baseline, target, timeframe, and decision ruleVanity metrics and unmeasurable success criteria
5Security & Compliance — SOC2, NIST, PCI, HIPAA frameworks mapped automatically to requirementsCompliance gaps caught post-build
6UI is First-Class — all UI states, transitions, and accessibility requirements included in BDD SpecUI states left undefined until QA
7Evidence Over Assumption — all claims labelled Strong / Medium / Weak with evidence citedOpinion-driven decisions presented as facts
8Spec Integrity / Spec Quality Score — 7-dimension scoring before any AI generation is allowedIncomplete or ambiguous specs fed to AI tools

Coverage & Traceability — Guardrails 9–11

#GuardrailWhat it blocks
9Acceptance Coverage Rule — every REQ-* must link to ≥1 BS-* and ≥1 TS-* before acceptanceUntested requirements reaching production
10Bidirectional Traceability — RTM-lite enforces forward (REQ→BS→TS) and backward (TS→BS→REQ) trace; orphan detectionTest cases with no requirement; scenarios with no test
11Scenario Completeness — each REQ-* must have a happy path + failure + edge case scenarioRequirements covered only by the "happy path"

BDD Quality — Guardrails 12–13

#GuardrailWhat it blocks
12No Ambiguity Rule — bans "should", "user-friendly", "fast", "seamless" in requirements and Then clauses; requires measurable replacementsVague specs that break AI generation and QA validation
13Automation Readiness Rule — every scenario classified Automatable / Partially automatable / Manual; flags Automation Risk if <50%Unclassified test cases in CI planning

OKR Alignment — Guardrail 14

#GuardrailWhat it blocks
14OKR Alignment Rule — every PRD must declare OBJ-*/KR-* linkage with a falsifiable contribution hypothesis and validation plan before proceeding to BDD Spec. Non-OKR work must carry an explicit exception declaration. OKR decoration rejected.Features built without a clear hypothesis for KR movement

Prioritization — Guardrails 15–18

#GuardrailWhat it blocks
15Prioritization Justification Rule — every priority decision must state: why now, KR value, what NOT doing, consequence of delay. Ranking without reasoning is not prioritization.Gut-based priority decisions with no audit trail
16Trade-off Declaration — every deprioritized item must record: why ranked lower, risk accepted, trigger for re-prioritizationSilent deferrals and "we'll get to it later" non-decisions
17Prioritization Gate — blocks PRD without Strategic Prioritization; blocks Issues without Delivery Prioritization. Specification before prioritization is the most expensive anti-pattern in product development.Full specs written for low-priority or unscored work
18Re-prioritization Trigger — defines evidence required to change order (data change, KR shift, effort change >50%, dependency change, competitor action). Opinion alone is not sufficient.Priority churn driven by stakeholder pressure, not data

Spec Quality Score — Guardrail #8

Before generating tests or code from the BDD Spec, the skill scores it across 7 dimensions. Generation is blocked unless the score is Complete.

Critical
Coverage
Happy paths, edge cases, and failure paths all present for every REQ-*
Critical
Clarity
No "should", "may", "typically" in Then clauses — all assertions exact
Required
Observability
Every Then clause names a system layer: UI element, API response, DB record, log entry, or event
Required
Linkage
Every BS-* scenario linked to at least one REQ-*
Required
Decisions
No open [MPD] markers remaining in the spec
Required

Conditional

OKR → Spec Traceability Chain

Every artifact in Product Ready is traceable upward to a company Objective and downward to a test case. Nothing exists without a reason to exist.

RTM-lite
Coverage Matrix
OKR contribution hypothesis
Every PRD must declare: what specific behaviour change does this feature drive, how does that translate into KR movement, and what data at 30/60/90 days proves or disproves it? Vague alignment is OKR decoration — rejected.
Bidirectional enforcement
RTM-lite enforces traceability in both directions. Forward: every REQ-* has a BS-* and TS-*. Backward: every TS-* traces to a BS-* and REQ-*. Orphan BS-*/TS-* are flagged and must be resolved before acceptance.
